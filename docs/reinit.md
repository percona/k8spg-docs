# Reinitializing replicas

When you create a new PerconaPGCluster, replicas will be created using `basebackup`. After instances are ready operator will automatically create a full backup and once backup finishes successfully, `pgbackrest` will be **prepended** to `create_replica_methods` so new replicas will be created using `pgbackrest`.

WARNING: Even if Patroni instance configurations will be updated to prepend `pgbackrest` to `create_replica_methods`, operator won't run `patronictl reload` in old replicas.

## Reinitializing by deleting replica Pod and its PersistentVolumeClaim

You can force reinitialization by deleting the Pod and its PersistentVolumeClaim:

```
$ kubectl delete pvc/cluster1-instance1-24b8-pgdata pod/cluster1-instance1-24b8-0
persistentvolumeclaim "cluster1-instance1-24b8-pgdata" deleted
pod "cluster1-instance1-24b8-0" deleted
```

Reinitialization will use whatever method is configured in this instance's Patroni configuration. For `cluster1-instance1-24b8-0`, configuration can be found in its respective ConfigMap:

```
$ kubectl get cm cluster1-instance1-24b8-config
NAME                             DATA   AGE
cluster1-instance1-24b8-config   1      95m
```

## Reinitializing by `patronictl reinit`

You can reinitialize a replica using `patronictl reinit`. Note that configuration in ConfigMap might not have applied to running Patroni instance. It's recommended to run `patronictl reload` before running `patronictl reinit`.

For example:

```
$ kubectl exec -it cluster1-instance1-24b8-0 -- cat /etc/patroni/~postgres-operator_instance.yaml
# verify the configuration

$ kubectl exec -it cluster1-instance1-24b8-0 -- patronictl reload cluster1-ha cluster1-instance1-24b8-0
```

## Configuring create_replica_methods

If you want to change `create_replica_methods` list for any reason you can use `spec.patroni.create_replica_methods` field:

```
apiVersion: pgv2.percona.com/v2
kind: PerconaPGCluster
metadata:
  name: cluster1
spec:
  patroni:
    createReplicaMethods:
    - basebackup
    - pgbackrest
  ...
```

Once you apply this configuration, operator will update Patroni instance ConfigMaps:

```
$ k get cm cluster1-instance1-24b8-config -o yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster1-instance1-24b8-config
data:
  patroni.yaml: |
    # Generated by postgres-operator. DO NOT EDIT UNLESS YOU KNOW WHAT YOU'RE DOING.
    # If you want to override the config, annotate this ConfigMap with pgv2.percona.com/override-config=true
    kubernetes: {}
    postgresql:
      basebackup:
      - waldir=/pgdata/pg17_wal
      create_replica_methods:
      - basebackup
      - pgbackrest
      pgbackrest:
        command: '''bash'' ''-ceu'' ''--'' ''install --directory --mode=0700 "${PGDATA?}"
          && exec "$@"'' ''-'' ''pgbackrest'' ''restore'' ''--delta'' ''--stanza=db''
          ''--repo=1'' ''--link-map=pg_wal=/pgdata/pg17_wal'' ''--type=standby'''
        keep_data: true
        no_leader: true
        no_params: true
      pgpass: /tmp/.pgpass
      use_unix_socket: true
    restapi: {}
    tags: {}
```

After the ConfigMap is updated, there will be some propagation period for changes to be reflected to mounted files in containers. You can check if the changes are propagated by manually checking the file:


```
$ kubectl exec -it cluster1-instance1-24b8-0 -- cat /etc/patroni/~postgres-operator_instance.yaml
# Generated by postgres-operator. DO NOT EDIT UNLESS YOU KNOW WHAT YOU'RE DOING.
# If you want to override the config, annotate this ConfigMap with pgv2.percona.com/override-config=true

  basebackup:
  - waldir=/pgdata/pg17_wal

  - basebackup
  - pgbackrest

    keep_data: true
    no_leader: true
    no_params: true
  pgpass: /tmp/.pgpass
  use_unix_socket: true

```
